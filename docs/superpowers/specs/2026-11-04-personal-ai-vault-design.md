# Personal AI Vault 教学 Demo 设计

## 1. 意图

这是一个用于学习 Android 开发的真实小应用，也是一个可以长期使用的个人 AI 资料库。

用户可以随手记录文字，后续再加入图片和录音。原始材料始终保留在手机本地，AI 只生成独立的解析结果。应用按日期生成每日 Markdown，并允许用户围绕本地资料聊天，让 AI 在回答时尽量调用相关的历史记录、近期摘要，以及后续由用户确认的长期资料，而不是只理解当前一句话。

教学目标与产品目标同等重要：每个阶段都必须能独立运行、容易验证，并且只引入少量新概念。

## 2. 目标

- 提供一个低摩擦的记录页面，能够输入并保存文字记录；默认归入今天，也允许选择过去的内容日期来补录旧随记。
- 原始记录只保存在应用私有的本地空间，不被 AI 结果覆盖。
- 支持手动触发 AI 整理当天记录，生成独立的每日 Markdown。
- 每日整理可按用户开关包含：
  - 任务与提醒
  - 温和、克制的建议
  - 值得继续思考的哲学问题
  - 当日摘要
- 提供基于本地资料的聊天界面；回答应显示使用了哪些日期或记录作为依据。
- 后续逐步加入图片、录音、自动定时整理、通知、新闻推荐和更强的检索。
- 通过实际代码讲清楚 Compose UI、状态、ViewModel、Room、本地文件、网络请求、后台任务和测试等 Android 基础。

## 3. 非目标

第一条完整主流程不包含：

- 用户账号、云同步或多设备同步。
- 多用户共享空间。
- 一开始就实现图片、录音和新闻联网搜索。
- 一开始就使用向量数据库或复杂的智能体框架。
- 让 AI 修改、删除或替代原始记录。
- 把所有历史资料无选择地发送给模型。
- 面向公开发布的完整商业级后端。

## 4. 反目标

即使功能可以运行，出现下列情况也视为失败：

- 为了展示技术而一次引入大量框架，使初学者无法理解数据如何流动。
- AI 输出看起来像事实，却无法追溯到使用过的本地记录。
- API 密钥硬编码进源码或提交到版本控制。
- 总结失败时破坏原始记录。
- 后台自动发送资料，但用户不知道发送了什么或无法关闭。
- 新闻推荐与本地记录混在一起，让用户无法区分个人资料和外部内容。

## 5. 已确认约束

- 当前项目是单模块 Android 应用，使用 Kotlin、Jetpack Compose 和 Material 3。
- 第一阶段本地优先，不建设云端资料存储。
- 原始内容与 AI 解析内容分开保存。
- 用户希望逐步开发，每一步都理解相关基础。
- AI 通过外部 API 调用；具体供应商不绑定在领域层。
- 自动整理既要支持手动触发，后续也支持每日定时触发。
- 任务提醒、温和建议、哲学问题和新闻推荐均为可选能力。

## 6. 方案比较

### 方案 A：所有功能一次完成

同时实现文字、图片、录音、AI 整理、聊天、定时任务和新闻。能够较快看到完整功能清单，但代码量和故障面太大，不适合第一次学习 Android。

### 方案 B：先分别学习技术模块

依次学习 Compose、数据库、文件和网络，最后再拼装产品。知识结构完整，但较长时间看不到真正可用的产品主流程。

### 方案 C：先完成一条端到端主流程，再扩展（已选择）

先实现“文字记录 → 本地保存 → AI 生成每日 Markdown → 基于资料聊天”，再加入媒体、自动化和外部内容。每一阶段都能运行，既能验证产品价值，也便于理解代码。

## 7. 产品结构

### 7.1 今天

首页展示：

- 当前正在记录的内容日期，默认为今天。
- 日期选择入口，允许选择今天或过去的日期来补录旧内容。
- 一个多行文字输入框。
- 保存按钮；保存后自动归入所选日期。
- 所选日期的记录时间线。
- “整理今天”按钮。
- 当天整理状态：未整理、处理中、已完成或失败。
- 当日摘要入口。

保存记录只写入本地，不自动调用 API。记录同时保存“内容日期”和“加入 App 的时间”：每日归档与 AI 整理依据内容日期，审计与排序冲突则使用加入时间。第一版不允许把普通随记归入未来日期；未来时间属于任务截止日期，由任务功能单独处理。

### 7.2 每日内容

每日内容分为两部分：

- 原始记录：按时间展示，只读呈现，允许用户明确发起编辑或删除。
- AI Markdown：独立文件，包含当日摘要、任务、温和建议和哲学问题。

重新整理当天时，从仍然存在的原始记录重新生成当前 Markdown。写入采用临时文件加原子替换，失败时保留上一份可用结果。

原始记录被编辑后，对应日期的 DailyAnalysis 立即标记为失效并停止用于聊天，直到用户重新整理。原始记录被删除后，同时删除可能仍包含该内容的当日 Markdown，并将该日标记为待重新整理，避免已经删除的内容继续被检索或发送给 API。

### 7.3 聊天

聊天页包含：

- 消息列表。
- 输入框和发送按钮。
- 本次回答引用的资料范围，例如“参考：11 月 2 日、11 月 4 日”。
- 无 API、离线或上下文不足时的明确提示。

聊天不会默认发送整个资料库。它先在本地选取相关内容，再把有限上下文交给 AI。

### 7.4 设置

设置页包含：

- API 地址。
- 模型名称。
- API 密钥输入与删除。
- 每日输出开关：任务、温和建议、哲学问题。
- 后续加入的自动整理时间与新闻推荐开关。
- 隐私说明：哪些内容保存在本地，何时会被发送给 API。

## 8. 数据与文件设计

### 8.1 Room 数据库

第一阶段使用 Room 保存结构化元数据：

#### Capture

- id
- type：第一阶段仅 TEXT，后续加入 IMAGE、AUDIO
- textContent：文字或转写文本
- localFilePath：图片或录音路径，第一阶段为空
- contentAt：用户选择的内容时间；第一版日期由用户选择，时间可使用保存时刻
- importedAt：内容加入 App 的真实时间
- updatedAt
- dayKey：由 contentAt 按本地时区得到的日期，如 2026-11-04
- processingState

#### DailyAnalysis

- dayKey
- markdownPath
- generatedAt
- sourceFingerprint：用于判断原始记录是否在上次整理后发生变化
- modelName
- status
- errorMessage

#### ChatMessage

- id
- role
- content
- createdAt
- referencedCaptureIds
- referencedDayKeys

Room 负责查询、排序、状态和关联；大文件与 Markdown 不作为数据库大字段保存。

### 8.2 应用私有文件

建议目录：

```text
files/
  raw/
    images/
    audio/
  analysis/
    daily/
      2026-11-04.md
```

第一阶段只会产生 `analysis/daily/*.md`。图片和录音目录在对应里程碑再启用。

### 8.3 API 密钥

API 密钥不写入源码、资源文件或版本控制。用户在设置页输入后，使用 Android Keystore 保护的本地加密存储。日志中不得输出密钥、完整请求正文或私人记录。

## 9. AI 边界

领域层定义供应商无关的接口：

- `DailyAnalyzer.analyze(day, captures, options)`
- `PersonalChat.reply(question, context)`

网络实现支持可配置的 OpenAI-compatible HTTP 接口，便于后续切换供应商。具体请求格式由数据层适配，UI 和领域逻辑不依赖供应商品牌。

每日分析优先要求模型返回结构化结果，再由应用本地生成 Markdown，避免直接信任任意 Markdown 文本。结构至少包含：

- summary
- tasks
- gentleSuggestions
- reflectionQuestions

聊天回答应同时返回引用的本地记录标识或日期；界面将这些引用展示给用户。

## 10. 本地上下文选择

第一版不使用向量数据库，采用容易理解和调试的检索：

1. 始终加入用户当前问题。
2. 加入最近几天的每日摘要，数量受上下文预算限制。
3. 从 Capture 和仍然有效的 DailyAnalysis 中按关键词、日期和简单相关度选取片段；失效分析不得进入上下文。
4. 去重并限制总字符数。
5. 将最终选择的日期和记录 ID 保存到 ChatMessage。

前三个里程碑不保存 AI 自动推断的永久用户画像，只使用原始记录和每日摘要。后续可增加一份用户可查看、修改的长期资料；AI 只能提出候选内容，必须经用户确认后才能写入。

后续资料量明显增长后，再增加全文搜索、嵌入和向量检索。无论采用何种检索，引用追踪都保留。

## 11. 自动整理与通知

第一条主流程只提供“整理今天”按钮，先验证数据与 AI 输出。

后续使用 WorkManager 添加每日定时任务：

- 用户选择时间并明确开启。
- 任务只在存在未整理的新记录时调用 API。
- 无网络时重试，不破坏已有 Markdown。
- 完成后发送通知，点击进入当日摘要。
- 用户可随时关闭自动整理。
- Android 的后台调度不保证精确到分钟，界面不得承诺精确时间。

## 12. 新闻推荐

新闻是独立的后续模块，因为它需要外部搜索或新闻数据源：

- 默认关闭。
- 外部新闻内容与个人记录在 UI 和 Markdown 中明确分区。
- 显示来源、发布时间和链接。
- 只把用户主动允许的兴趣摘要发送给新闻服务。
- 不允许模型凭空生成“新闻”。

## 13. 架构边界

采用对初学者可解释的分层，不引入过度复杂的多模块：

- Compose Screen：只负责展示状态和发送用户事件。
- ViewModel：管理页面状态和调用用例。
- Use case / service：保存记录、生成每日分析、构建聊天上下文。
- Repository：统一访问 Room、文件和网络。
- Room / file store / API client：具体数据来源。

使用协程和 Flow 传递异步状态。第一阶段保持单 app 模块；当功能和测试明显增长后再讨论拆分模块。

## 14. 失败处理

- 没有 API 配置：保留本地记录，提示前往设置，不发起请求。
- 无网络或超时：标记分析失败，允许重试，保留旧 Markdown。
- API 返回格式不合法：不覆盖旧文件，保存可诊断但不含私人正文的错误。
- 当天没有记录：不调用 API，提示暂无可整理内容。
- 用户在分析期间新增记录：本次结果关联 sourceFingerprint，并提示存在尚未整理的新内容。
- 用户向过去日期补录文字或媒体：对应日期的 DailyAnalysis 标记失效，等待用户重新整理；不会错误地归入导入当天。
- 用户编辑原始记录：对应 DailyAnalysis 标记失效，旧 Markdown 不再进入聊天。
- 用户删除原始记录：删除该日旧 Markdown，防止已删除内容继续存在于衍生文件中；用户可重新整理剩余记录。
- 应用重启：处理中状态可恢复为可重试，不永久卡住。
- 聊天检索不到资料：明确说明回答缺少个人上下文，不伪造引用。

## 15. 隐私与用户控制

- 原始资料默认仅在应用私有目录。
- 只有用户主动触发或明确开启的后台任务可以向 API 发送内容。
- 每次发送前可在后续版本提供“将发送哪些资料”的预览。
- 用户可以单独删除 AI 分析而不影响原始记录；但删除原始记录会使对应分析失效，并删除可能含有该内容的当日 Markdown。
- 长期资料必须可查看、可修改、可删除；AI 推断只有在用户确认后才能成为长期资料。
- 卸载应用会删除应用私有数据；备份与导出属于后续功能。
- 第一版设计为个人学习项目，不宣称端到端加密或医疗、心理咨询能力。

## 16. 分阶段交付

### 里程碑 1：可用的本地文字日记

学习：Compose、状态、列表、ViewModel、Room、Flow。

完成：

- 今天页。
- 新增文字记录。
- 选择今天或过去日期，补录旧随记并自动归档到所选日期。
- 展示所选日期的记录。
- 重启应用后数据仍存在。
- 基础单元测试和数据库测试。

### 里程碑 2：AI 每日 Markdown

学习：设置页、Keystore、网络请求、JSON、协程错误处理、文件写入。

完成：

- API 配置。
- 手动“整理今天”。
- 可选输出项。
- 生成独立 Markdown。
- 失败重试与旧结果保护。
- 使用假 API 的测试。

### 里程碑 3：基于资料聊天

学习：多页面导航、聊天 UI、上下文构建、检索、引用展示。

完成：

- 聊天页。
- 本地关键词与近期摘要检索。
- 有预算限制的上下文组装。
- 回答引用日期和记录。
- 检索与上下文构建测试。

### 里程碑 4：图片与录音

学习：Activity Result API、权限、文件、MediaRecorder 或系统选择器、转写接口。

完成：

- 导入或拍摄图片。
- 录音或选择音频。
- 为导入的图片或音频选择内容日期；图片元数据存在可靠拍摄日期时可作为默认值，用户仍可修改。
- 保存原始文件并按内容日期归档。
- 图片描述和语音转写。
- 将媒体解析文本纳入每日整理和聊天检索。

### 里程碑 5：自动整理与提醒

学习：WorkManager、通知权限、后台约束。

完成：

- 用户可选每日整理时间。
- 新内容检测。
- 自动分析、重试和完成通知。
- 任务提醒的本地呈现。

### 里程碑 6：可选新闻与高级检索

学习：外部数据源、来源展示、全文搜索或向量检索。

完成：

- 默认关闭的新闻模块。
- 有来源的推荐。
- 资料增长后的检索升级。
- 用户可确认和编辑的长期资料，不自动保存 AI 推断。
- 导出与备份方案评估。

## 17. 验证标准

每个里程碑必须满足：

- Debug 构建成功。
- 核心逻辑有自动化测试。
- 关键页面可在模拟器或预览中验证。
- 离线、空数据和失败状态有可见反馈。
- 不在日志或仓库中泄露 API 密钥和私人正文。
- 教学说明能够解释本阶段新增的数据流：用户操作如何经过 UI、ViewModel、Repository，最终写入数据库、文件或网络。

第一条主流程完成的验收场景：

1. 用户输入两条今天的文字并保存。
2. 用户选择一个过去日期补录旧随记，记录出现在所选日期而不是导入当天。
3. 杀掉并重新打开应用，记录仍存在。
4. 用户配置 API 并点击“整理今天”。
5. 应用生成当日 Markdown，原始记录不变。
6. 用户在聊天页提出与记录相关的问题。
7. 回答引用了对应日期或记录；无相关资料时明确说明。

## 18. 留给实现计划的决定

这些选择不会改变产品边界，可由实现计划根据项目当前版本与兼容性决定：

- Room、Navigation、网络客户端和序列化库的具体稳定版本。
- Markdown 第一阶段使用纯文本展示还是轻量渲染。
- Repository 和 use case 的具体包名。
- 每个里程碑内部的最小提交拆分。
- API 结构化响应的具体 schema 名称与序列化实现。
